# rPPG 改善計畫（2026-07-04）

> 對應三線升級計畫階段 2b。定位：把 2026-07-04 首次實錄驗證的結論，轉成
> 「rPPG 準確度還能怎麼變準」的可執行路線圖與斷點續接指引。本文件**只規劃、不動數值**。
> 前置事實見 `docs/2026-07-04-p6b4-first-belt-truth-validation.md`。

## 使用者的核心疑問：戴著心跳帶一直測，rPPG 就會自己調好嗎？

**部分會、部分不會，且「會」的那塊空間很小。**

- **會自動變好的部分**：`OnlineBpmCalibrator`（`rppg/adaptive_calibration.py`）在勾選
  「心跳帶真值校準（背景）」時，以心跳帶 BPM 為真值、對 rPPG 原始 BPM 的中位殘差做
  低增益 EMA，慢速微調 offset；收斂後存成新校準版本、跨 session 持續套用。這部分確實
  「一直測就會累積改善」，且不需你做任何事，只要背景勾著。
- **不會自動變好的部分（且是誤差主體）**：實錄 155 視窗中，整體 MAE 10 BPM 的 **79%**
  來自「半頻/諧波鎖定」離群視窗（rPPG 鎖到真值的一半 41–60，或諧波 ~144）。這類錯誤
  **不是 offset 能修的**（offset 是全域平移，救不了個別視窗鎖錯頻率），也不是繼續錄更久
  會消失的——它是 Welch 峰選在低 SNR 片段挑錯峰的結構性問題。
- **佐證**：排除離群後穩態 MAE 僅 2.73 BPM、有號偏差中位 +0.09 BPM。也就是**鎖對頻率時
  rPPG 已經很準**，offset 幾乎無殘差可修。真正的槓桿在「讓它鎖對頻率」，不在校準 offset。

**結論給使用者**：日常照常用、背景勾著校準即可，offset 那塊會自己慢慢好。但要讓 rPPG
「準到不需心跳帶」，得動 Welch 峰選邏輯——那是重量級數值路徑，列在下方，動之前會先問你。

## 為什麼 ROI 權重自適應（P6b 那條線）不是答案

實錄掃描 10 組 ROI 權重，**無一組**超過 0.5 BPM 採用門檻——因為半頻/諧波鎖定時，四個
ROI 是**同時**鎖錯，換權重換不掉共同的失敗。這正面驗證了 P6b 的 A/B 護欄會正確地
「什麼都不採用」，也說明 `rppg_param_tuning_enabled` 維持 OFF 是對的。ROI 權重不是槓桿。

## 候選改善方案（皆屬重量級數值路徑，需使用者裁決）

以下針對「半頻/諧波鎖定」，按風險由低到高排序。**共同前提**：先在離線回放上驗證有效
再考慮進 live，不直接改即時路徑。

### 方案 A：諧波約束峰選（harmonic-aware peak selection）
- 想法：Welch PSD 選峰時，不只挑最高峰，而是比較 `f` 與 `2f`/`0.5f` 的能量關係，
  用「基頻通常能量最強、諧波為其分量」的先驗，避免把 0.5f（半頻）或 2f（諧波）當基頻。
- 風險：低 SNR 時諧波能量可能反超基頻，硬約束可能把「真的是那個頻率」的情況改錯；
  需以離線資料調閾值。相對溫和，是首選嘗試。

### 方案 B：生理合理性 + 時序連續性約束
- 想法：BPM 落在合理生理帶（如 40–180）內才接受；且限制相鄰視窗的 BPM 跳變速率
  （心率不會 3 秒內從 90 掉到 45），用前一視窗的可信 BPM 約束當前選峰。
- 風險：連續性約束會讓真實的快速心率變化（運動後）反應變慢；需在「抗跳變」與
  「即時性」間取捨。可與方案 A 疊加。

### 方案 C：訊號品質門檻拒絕輸出
- 想法：當視窗 SNR/SQI 過低時，寧可不輸出 BPM（顯示「訊號不足」）也不輸出鎖錯的值。
- 風險：會降低 BPM 的輸出覆蓋率（可用時間變少）；但對疲勞融合而言，rPPG 只佔 15% 且
  SQI 不足時本就降權，拒絕輸出可能比輸出錯值更安全。副作用最小、但不「修好」只是「不輸出」。

**建議順序**：先 A（治本、風險中等）→ 視效果疊 B → C 當保底。

## 驗證方法（已有基建，不需硬體重錄）

- 用既有 belt-truth capture（`recordings/belt_truth_capture/*.jsonl`）與離線重算函式
  `rppg.adaptive_calibration.recompute_raw_bpm_from_roi_windows` 家族做 A/B：改前 vs 改後
  對同一段錄製重算 BPM、對心跳帶真值算 MAE，特別看**離群視窗數是否下降**（這才是目標，
  不是穩態 MAE，穩態已經很好）。
- 參考 `scripts/rppg_param_replay.py` 的滑動視窗 + MAE 比較骨架，改峰選邏輯後可沿用。
- **關鍵指標**：不是整體 MAE，而是「absolute error > 15 BPM 的視窗數」（實錄基準：34/155）。
  改善有效 = 這個數字明顯下降且穩態視窗不退化。
- 先離線證明有效，再討論是否進 live（live 改的是即時 BPM 輸出，風險高，需完整重量級流程）。

## 斷點續接指引

- **現況**：offset 校準已上線且會自動累積改善；半頻/諧波抑制**尚未動任何碼**。
- **下一步（若要做）**：先在離線回放實作方案 A 的原型（改 `welch_peak_hz` 或其呼叫端的
  峰選，加諧波比較），用 belt-truth capture 量「離群視窗數」降幅。**這是動 `rppg/` 數值
  路徑 = 重量級任務**：完整 pytest + golden check（本機無 UTA 資料集則靠 bit-identical
  單元測試 + 完整 pytest）+ 數值行為影響聲明 + 先問使用者。
- **紅線**：不得無聲改變既有 BPM 輸出；任何會變的值要寫數值行為影響聲明。
- **注意**：需要更多場景的 belt-truth 錄製（低光、動作、不同心率區間）才能確認方案在
  各條件下都降離群、不引入新錯誤——目前只有單段 8 分鐘、靜坐、80–110 BPM 的錄製。
