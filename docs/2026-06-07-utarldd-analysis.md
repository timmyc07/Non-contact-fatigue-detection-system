## 0. 畢專主旨校正：無人機駕駛員疲勞監測

本專題主旨是「監測無人機駕駛員的疲勞狀態」，不是汽車駕駛分類器，也不是醫療診斷系統。系統應被描述為：使用一般攝影機與桌面 GUI，在無人機遠端操作員長時間監控、判斷與操控任務時，追蹤臉部/眼部行為疲勞特徵、頭部姿態、視線穩定度與 rPPG 輔助生理品質，提供警覺度下降的早期提示與可回放紀錄。

UTA-RLDD 在本專題中的角色是「替代短期內難以大量募集無人機操作員資料的回放驗證資料集」。它提供 Alert、Low Vigilant、Drowsy 三類長影片，可用來檢查 PERCLOS、眨眼時序、狀態比例與融合分數是否有合理趨勢；但它不能取代無人機地面站場域測試，也不能把本專題主軸改成汽車駕駛嗜睡分類。畢專報告與口試應把 UTA-RLDD 放在「驗證方法」章節，而非「專題目的」章節。

## 1. 測試範圍與資料定義

本次批次回放使用 UTA-RLDD `Fold1_part1` 的 12 位受試者，每位受試者各有 `0 / 5 / 10` 三段影片，共 36 支影片。UTA-RLDD 官方標籤定義為：

- `0 = Alert`
- `5 = Low Vigilant`
- `10 = Drowsy`

本專案目前把 UTA-RLDD label 視為「整段影片類別」，不是逐幀 ground truth。因此報告只能判斷三類影片的統計趨勢是否支持系統，不應宣稱逐幀分類準確率。

## 2. 「滿分」或「接近 100%」的判斷方式

若提到「滿分」或「接近 100%」，本次只能用在下列兩個工程可用性指標：

1. 影片處理完成率：36 支影片全部 `done`，完成率為 100%。
2. 人臉偵測率：三類影片平均都接近 100%，整體平均約 99.93%。

這不代表疲勞辨識準確率接近 100%，也不代表 Alert / Low Vigilant / Drowsy 三分類已經可靠。實際上，validation report 的結論是「目前不支持分類有效」。因此在畢專報告與口試中，建議使用「處理完成率 100%」、「平均人臉偵測率約 99.93%」這種精確說法，避免使用「模型滿分」或「分類滿分」。

### 3.1 UTA-RLDD 影片級三分類對照表

依使用者附圖需求，以下把 UTA-RLDD 回測標籤與本系統輸出整理成「UTA 受試者資料 × 本系統判讀」的三分類矩陣。這張表只做**影片級粗略對齊**，不是逐幀 accuracy，也不能直接代表正式三分類準確率。三分類規則如下：

- UTA-RLDD 參考：`0 = Alert` 對應清醒；`5 = Low Vigilant` 對應低警覺；`10 = Drowsy` 對應疲勞。
- 本系統輸出：`未見明顯疲勞` 對應清醒；`可能低警覺` 對應低警覺；`高疲勞跡象` 對應疲勞。
- 表格欄位是 UTA 受試者資料，列是本系統判讀；每一欄的分母都是該 UTA 類別的 12 支影片。

| 你們的判讀 \ UTA 受試者資料 | 清醒 | 低警覺 | 疲勞 |
| --- | ---: | ---: | ---: |
| 清醒 | 2/12 | 1/12 | 2/12 |
| 低警覺 | 10/12 | 8/12 | 6/12 |
| 疲勞 | 0/12 | 3/12 | 4/12 |

黃色對角線代表本系統與 UTA 影片級參考相符，合計為 14/36；非對角線代表不相符，合計為 22/36。三分類矩陣顯示，本系統目前最能對齊的是 UTA 低警覺類，12 支中有 8 支被判為低警覺；但 UTA 清醒類有 10/12 支被判為低警覺，代表清醒誤報偏高。UTA 疲勞類只有 4/12 支被判為疲勞，另有 6/12 支被降判為低警覺、2/12 支被判為清醒，代表重度疲勞敏感度仍不足。整體而言，本系統比較像「早期風險提醒器」，容易把清醒或疲勞邊界推向低警覺，不適合宣稱已能穩定完成清醒、低警覺、疲勞三分類。

同一批資料若改用 validation report 的受試者趨勢檢查，12 位受試者中只有 4 位支持、8 位不支持。因此上表適合放在簡報或報告中說明「本系統對低警覺訊號較敏感，但清醒誤報與疲勞低估都偏高」，不適合宣稱疲勞三分類已達穩定可用程度。

## 4. 系統缺陷分析

### 4.1 分類與門檻尚未被資料集支持

validation report 顯示同一受試者三段影片的趨勢支持度不足。完整上升比例很低，Drowsy 高於 Alert 的比例也不足以支持可靠三分類。這代表目前不能把系統包裝成「已完成疲勞三分類模型」，只能說是「可解釋疲勞特徵擷取與警示原型」。

### 4.2 Alert 誤報偏高

Alert 類別仍有約 29.43% frame 被判成 `LOW_VIGILANCE`。這會造成展示或實際使用時的 false alarm 風險。造成原因可能包含眨眼時序 baseline 尚不穩、低警覺門檻偏敏感、部分受試者的自然眼型/姿態與系統假設不同，以及 UTA-RLDD 影片畫面條件與本專案場域不同。

### 4.3 Drowsy 漏報明顯

Drowsy 類別平均融合分數只有 0.054，95 分位融合分數只有 0.134，低於 Alert 的 0.156。多支 Drowsy 影片未出現明顯 `DROWSY` 或 `CRITICAL` frame，代表系統對「整段主觀嗜睡」的敏感度不足。若使用者只是低警覺、眼睛仍大多張開，本系統目前不一定能穩定抓到。

### 4.4 rPPG 可用性高，但不是疲勞分類答案

rPPG quality 與 SQI 平均都很高，代表 ROI 與訊號品質管線在這批影片上可用；但 UTA-RLDD 沒有同步 PPG/ECG ground truth，不能用它驗證 BPM 絕對準確率。rPPG 目前適合作為生理負荷輔助與診斷欄位，不宜在兩週內提高成疲勞主判定。

### 4.5 文件與編碼品質仍需整理

部分 CLI 說明與舊文件曾出現亂碼，這會影響畢專報告與專案交付觀感。即使演算法不再大改，也應在收尾期間修正 README、CLI help、報告章節與截圖素材，讓展示路徑清楚可信。

### 4.6 報表分母與校準隔離需要改善

目前 replay summary 的平均疲勞分數、融合分數與 PERCLOS 會受到 `CALIBRATING`、`NO_FACE` 或尚未具備 behavior-available frame 影響。這對完整工程紀錄合理，但若直接拿來代表「有效疲勞判讀平均」，會偏低或被前段校準稀釋。下一版報表應另外列出 post-calibration、face-detected、behavior-available 的有效分母與平均值。

此外，`FatigueEngine` 可能載入持久化 blendshape baseline。若本機曾用真人 webcam 校準，UTA-RLDD replay 可能不是完全乾淨的資料集基準。兩週內最務實的修法，是為 dataset replay 建立獨立 calibration namespace，或在 replay 模式停用持久化校準讀寫，確保每次資料集驗證可重現。

## 5. 目前是否可當畢業專題

可以，但定位要正確。

目前專案已經具備畢業專題可展示的工程完整度：桌面 GUI、即時相機、MediaPipe 臉部特徵、rPPG、疲勞行為特徵、融合分數、SQLite 紀錄、Web dashboard、UTA-RLDD replay、批次 CSV/HTML/manifest、測試與技術報告。這些足以構成一個完整的「無人機駕駛員非接觸式疲勞與警覺度監測系統原型」。

但目前不能把題目講成「已可靠辨識 Alert / Low Vigilant / Drowsy 的高準確率分類器」。比較適合的畢專說法是：

> 本專題完成一套可即時運作、可回放驗證、可記錄與可視覺化的非接觸式疲勞監測原型。UTA-RLDD 測試顯示系統在影片處理與人臉偵測上穩定，PERCLOS 等眼部閉合特徵對 Drowsy 類別有反應，但目前融合門檻尚未充分支持三分類，因此後續重點是以標註資料做門檻校正與 false alarm / miss rate 評估。

更貼近本專題主旨的口試說法是：

> 本專題面向無人機遠端駕駛員，目標是在長時間監控與操控任務中，使用一般攝影機即時觀察操作員的眼部閉合、眨眼時序、視線穩定、頭部姿態與 rPPG 輔助品質，提供疲勞或警覺度下降提示。UTA-RLDD 只作為早期回放驗證資料，用來檢查特徵趨勢與報表管線；最終門檻仍需使用無人機操作場域資料校正。

## 6. 兩週內收尾建議

### 第 1-2 天：固定展示主線

- 把題目定位成「疲勞監測原型與可重現驗證平台」，不要定位成高準確率分類器。
- 簡報第一頁直接寫「無人機駕駛員疲勞狀態監測系統」，UTA-RLDD 放在驗證章節，不放在研究目的。
- 準備 1 支 live camera 展示流程：開啟 GUI、偵測臉部、顯示 rPPG ROI、疲勞指標、錄影與 Web dashboard。
- 準備 2-3 支 UTA-RLDD 影片作為 replay demo：至少包含偵測穩定、Drowsy PERCLOS 較高、以及一支誤判案例。

### 第 3-5 天：補足報告與圖表

- 將本次 36 支影片結果整理成表格與長條圖：完成率、人臉偵測率、PERCLOS、融合分數、狀態比例。
- 在報告中加入「目前不支持分類有效」章節，主動說明限制，避免被口委追問時顯得被動。
- 加入系統架構圖、疲勞偵測流程圖、rPPG 流程圖與資料輸出流程。

### 第 6-8 天：做最小校正，不大改演算法

- 不建議兩週內大改 rPPG 或導入深度學習模型。
- 可新增一個離線分析 notebook 或 CSV 統計腳本，用固定報表產生圖表與結論。
- 若要微調門檻，只能用 feature flag 或另存校正版 config，並保留目前結果做 A/B 比較。
- 優先補 replay 報表的有效 frame 統計，並隔離資料集 replay 的 calibration，避免平均值被無效分母或本機舊 baseline 影響。

### 第 9-11 天：錄製展示素材

- 錄 GUI 操作影片、Web dashboard playback、UTA-RLDD replay 批次結果。
- 截圖包含：主視窗、ROI 標註、疲勞狀態、Web dashboard、CSV 摘要、validation report。
- 準備口試時可展示的「成功案例」與「限制案例」。

### 第 12-14 天：穩定化與口試包裝

- 跑一次 `pytest` 與必要 smoke test。
- 確認 README 從乾淨環境可照著啟動。
- 整理簡報：動機、方法、系統架構、即時 demo、UTA-RLDD 驗證、缺陷、未來工作。
- 把結論寫成「完成工程原型與驗證管線，分類門檻仍待資料校正」。

## 7. 不建議兩週內承諾的項目

- 不承諾 Alert / Low Vigilant / Drowsy 三分類準確率。
- 不承諾 rPPG BPM 醫療級準確。
- 不承諾可直接用於安全關鍵無人機操作。
- 不承諾對所有光線、眼鏡、姿態、膚色與攝影機都穩定。
- 不建議臨時導入 CNN/LSTM/Transformer，除非只是離線比較，不進主流程。

## 8. 結論

這個專案目前已可作為畢業專題，但應以「完整系統原型與驗證平台」交付，而不是以「高準確率疲勞分類器」交付。最新 UTA-RLDD 報表證明系統可以穩定處理長影片、保留逐幀資料、輸出可稽核指標；同時也誠實暴露融合分數與三分類標籤尚未對齊。兩週內最好的收尾策略，是強化報告、圖表、展示流程與限制說明，避免高風險大改演算法。
